## 1. API recon

API recon là giai đoạn thu thập bề mặt tấn công của API trước khi đi vào khai thác. Với web thông thường, mình có thể nhìn thấy nhiều chức năng trực tiếp trên UI. Nhưng với API, rất nhiều logic nằm ở request nền, JavaScript, mobile client, hoặc endpoint không được liên kết rõ ràng trên giao diện.

Mục tiêu của API recon là trả lời một vài câu hỏi chính:

- Ứng dụng đang gọi những endpoint nào?
- Endpoint nhận method nào: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`?
- Dữ liệu được truyền qua query string, path, header, cookie, hay request body?
- API dùng định dạng nào: JSON, XML, form-urlencoded, multipart, GraphQL, hay format tùy chỉnh?
- Có cơ chế xác thực nào: session cookie, bearer token, API key, CSRF token, OAuth token?
- Có endpoint nào chỉ xuất hiện trong JavaScript, documentation, hoặc response lỗi không?

Khi test API, mình thường bật Burp Proxy rồi thao tác toàn bộ chức năng trên website để tạo sitemap ban đầu. Sau đó xem kỹ các request có pattern như `/api/`, `/graphql`, `/v1/`, `/v2/`, `/internal/`, `/admin/`, `/user/{id}`, hoặc các file JavaScript có chứa route. Những thông tin nhỏ như status code, message lỗi, header `Allow`, schema trong response, hay object JSON trả về đều có thể gợi ý endpoint hoặc parameter ẩn.

Điểm quan trọng là không chỉ nhìn endpoint như một URL đơn lẻ. Một API endpoint thường là tổ hợp của path, method, header, body, quyền của user hiện tại, và trạng thái dữ liệu. Cùng một path nhưng đổi method từ `GET` sang `PATCH`, hoặc đổi `Content-Type` từ form sang JSON, có thể kích hoạt một nhánh xử lý hoàn toàn khác.

## 2. API documentation

API documentation mô tả cách client nên tương tác với API: endpoint, method, parameter, request body, response, authentication, và lỗi có thể trả về. Trong môi trường thật, documentation có thể được public cho developer, để quên trên production, hoặc chỉ dự định dùng nội bộ nhưng lại có thể truy cập từ internet.

Với attacker hoặc pentester, documentation rất có giá trị vì nó biến việc đoán mò endpoint thành đọc trực tiếp hợp đồng API. Nếu tài liệu liệt kê các endpoint nhạy cảm như tạo user, sửa role, cập nhật giá, xóa tài nguyên, export dữ liệu, hoặc chức năng admin, mình có thể kiểm tra xem server có enforce authorization đúng không.

### 2.1 Discovering API documentation

Một số đường dẫn phổ biến để tìm API documentation:

- `/api`
- `/api/docs`
- `/api/swagger`
- `/api/swagger.json`
- `/swagger`
- `/swagger-ui`
- `/swagger-ui.html`
- `/openapi.json`
- `/v1/openapi.json`
- `/docs`
- `/redoc`

Ngoài brute-force path, có thể tìm documentation trong JavaScript bundle, response header, HTML comment, file `robots.txt`, `sitemap.xml`, hoặc link bị ẩn trên trang. Nếu endpoint trả về lỗi kiểu "missing parameter" hoặc "unsupported method", lỗi đó đôi khi cũng tiết lộ format request đúng.

Khi tìm được documentation, nên thử các thao tác sau:

- Kiểm tra endpoint có yêu cầu authentication không.
- Dùng tài khoản quyền thấp để gọi endpoint quyền cao.
- Thử thay path parameter như username, user ID, product ID.
- Thử method khác với method được UI sử dụng.
- Xem schema request body có field nhạy cảm nào không, ví dụ `role`, `isAdmin`, `price`, `discount`, `owner`, `approved`.

### 2.2 Using machine-readable documentation

Machine-readable documentation là tài liệu API có cấu trúc để công cụ có thể đọc được, phổ biến nhất là OpenAPI/Swagger. Thay vì chỉ là trang HTML cho người đọc, file như `openapi.json` hoặc `swagger.json` mô tả endpoint, method, parameter, schema, kiểu dữ liệu, response code, và đôi khi cả security scheme.

Ví dụ, một OpenAPI spec có thể tiết lộ:

- Endpoint nội bộ không xuất hiện trên UI.
- Method nguy hiểm như `DELETE`, `PATCH`, `PUT`.
- Field ẩn trong body như `isAdmin`, `chosen_discount`, `stock`, `price`.
- Kiểu dữ liệu và ràng buộc validate của parameter.
- Version API cũ vẫn còn tồn tại, chẳng hạn `/api/v1/` bên cạnh `/api/v2/`.

Các công cụ như Burp Suite có thể import OpenAPI spec để tự động tạo sitemap và request mẫu. Sau khi import, mình có thể gửi từng request sang Repeater để kiểm tra authorization, validation, business logic, và những parameter không được UI expose.

Điểm cần chú ý là documentation không phải lúc nào cũng đúng tuyệt đối. Có trường hợp tài liệu cũ hơn code, hoặc code vẫn support field/method đã bị xóa khỏi tài liệu. Vì vậy, documentation nên được xem là bản đồ ban đầu, còn bước kiểm chứng vẫn phải dựa trên response thực tế từ server.

## 3. Identifying API endpoints

Nếu không có documentation, mình cần tự xác định endpoint thông qua traffic và asset của ứng dụng. Cách cơ bản nhất là thao tác từng chức năng trên UI rồi quan sát request trong Burp HTTP history. Các chức năng như login, profile, giỏ hàng, checkout, search, upload, comment, reset password thường sẽ gọi API phía sau.

Một số nguồn thường giúp tìm endpoint:

- Request trong Burp Proxy khi thao tác UI.
- JavaScript bundle chứa route hoặc tên function gọi API.
- File source map như `.map` nếu bị để lộ.
- Response lỗi có nhắc đến path, controller, object, hoặc field.
- Header `Allow` khi gửi sai method.
- CORS preflight request với method `OPTIONS`.
- Pattern URL có thể suy luận, ví dụ `/api/products/1/price` gợi ý có thể có `/api/products/{id}` hoặc `/api/products/{id}/stock`.

Khi đã tìm được endpoint, nên thử mở rộng theo nhiều chiều:

- Đổi method: `GET` sang `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`.
- Đổi ID hoặc username trong path.
- Thêm, bớt, hoặc sửa field trong JSON body.
- Đổi `Content-Type` để xem parser khác có được kích hoạt không.
- Thử truy cập endpoint khi chưa đăng nhập hoặc bằng user quyền thấp.

Rất nhiều lỗ hổng API không nằm ở endpoint đang được UI dùng, mà nằm ở endpoint "còn tồn tại nhưng không còn được gọi". Đây thường là chức năng cũ, chức năng admin, hoặc endpoint hỗ trợ mobile app/version cũ nhưng thiếu kiểm soát quyền.

## 4. Finding hidden parameters

Hidden parameter là parameter hoặc field mà server vẫn xử lý nhưng client bình thường không gửi. Trong API, hidden parameter đặc biệt nguy hiểm vì server thường bind toàn bộ JSON body vào object nội bộ. Nếu developer không kiểm soát field được phép cập nhật, attacker có thể tự thêm field nhạy cảm vào request.

Các cách tìm hidden parameter:

- So sánh response object với request object. Nếu response có field `role`, `discount`, `price`, `isAdmin`, có thể server cũng nhận field tương tự khi update.
- Đọc JavaScript để tìm tên field không xuất hiện trong UI.
- Dùng wordlist để fuzz parameter trong query string hoặc JSON body.
- Quan sát lỗi validation, ví dụ "unknown field", "invalid type", hoặc "field is read-only".
- Tìm trong documentation, schema, mobile API, hoặc endpoint version cũ.

Một dạng lỗi phổ biến là mass assignment. Lỗi này xảy ra khi server tự động map dữ liệu từ request vào model/database object mà không whitelist field được phép sửa. Ví dụ user chỉ nên đổi `email`, nhưng nếu request body có thêm `"isAdmin": true` và server lưu luôn field đó, attacker có thể leo quyền.

Khi test hidden parameter, nên đặc biệt chú ý các field liên quan đến quyền, tiền, trạng thái, chủ sở hữu, và workflow:

- `role`, `isAdmin`, `permissions`
- `price`, `discount`, `credit`, `balance`
- `owner`, `user_id`, `account_id`
- `status`, `approved`, `verified`
- `quantity`, `stock`, `limit`

## 5. Preventing vulnerabilities in APIs

Phòng tránh API vulnerabilities cần bắt đầu từ nguyên tắc: client không đáng tin. UI có thể ẩn nút, không gửi field, hoặc chỉ gọi một số endpoint nhất định, nhưng attacker có thể tự tạo request trực tiếp. Vì vậy mọi kiểm tra quan trọng phải nằm ở server.

Một số nguyên tắc quan trọng:

- Dùng allowlist cho method, endpoint, và field được phép xử lý.
- Enforce authentication và authorization ở từng endpoint, không dựa vào việc endpoint "không được hiển thị".
- Với object-level access control, luôn kiểm tra user hiện tại có quyền trên resource được yêu cầu hay không.
- Không bind toàn bộ request body vào model nhạy cảm nếu không lọc field.
- Validate kiểu dữ liệu, range, format, và quan hệ logic của input.
- Không để lộ API documentation, debug endpoint, hoặc version cũ trên production nếu không cần thiết.
- Tắt hoặc giới hạn method không dùng, đặc biệt `PUT`, `PATCH`, `DELETE`.
- Log các hành vi bất thường như gọi endpoint không dùng, fuzz parameter, đổi method liên tục.

Với API có nhiều client như web, mobile, partner integration, cần đảm bảo security rule được triển khai ở lớp backend chung thay vì rải rác theo từng client. Nếu không, một client cũ hoặc endpoint legacy có thể trở thành đường vòng để bypass logic mới.

## 6. Server-side parameter pollution

Server-side parameter pollution xảy ra khi attacker chèn thêm, sửa, hoặc phá vỡ parameter trong request bên ngoài, khiến server tạo ra một request nội bộ khác với ý định ban đầu. Nói ngắn gọn, input của người dùng được server dùng để dựng query string, REST path, hoặc structured data gửi tới backend/internal API mà không encode hoặc validate đúng.

Ví dụ, frontend gửi:

```text
POST /forgot-password
username=administrator
```

Server có thể dùng `username` để gọi nội bộ:

```text
GET /internal/users?username=administrator
```

Nếu attacker gửi username có chứa ký tự như `&`, `#`, `?`, `/`, hoặc sequence path traversal, request nội bộ có thể bị biến dạng. Tùy framework, backend có thể lấy parameter đầu tiên, parameter cuối cùng, nối giá trị lại, hoặc báo lỗi. Chính sự khác nhau này tạo ra cơ hội khai thác.

### 6.1 Testing for server-side parameter pollution in the query string

Với query string, mục tiêu là kiểm tra xem input bên ngoài có được nối thẳng vào query nội bộ không. Các ký tự đáng thử gồm:

- `&` để thêm parameter mới.
- `#` để cắt phần phía sau của query nếu không được encode.
- `%23` là dạng URL-encoded của `#`.
- `%26` là dạng URL-encoded của `&`.
- `=` để thử tạo cặp key/value mới.

Ví dụ nếu server nội bộ gọi:

```text
/internal/user?username=<input>&field=email
```

Attacker có thể thử input:

```text
administrator%26field=reset_token
```

Nếu server ghép chuỗi không an toàn, request nội bộ có thể có hai parameter `field`. Tùy backend lấy parameter nào, attacker có thể điều khiển field được trả về.

Khi test, nên quan sát kỹ response lỗi. Các message như `parameter is not supported`, `invalid field`, `missing parameter`, hoặc thay đổi độ dài response có thể cho biết request nội bộ đã bị ảnh hưởng.

### 6.2 Testing for server-side parameter pollution in REST paths

Trong REST API, dữ liệu thường nằm trực tiếp trong path thay vì query string, ví dụ:

```text
/api/users/{username}/field/{field}
```

Nếu server nhận username từ client rồi nối vào path nội bộ, attacker có thể thử các payload liên quan đến path traversal hoặc path confusion:

```text
../
..%2f
%2e%2e%2f
%252e%252e%252f
```

Mục tiêu là làm path nội bộ trỏ sang resource khác, field khác, hoặc file tài liệu như `openapi.json`. Tuy nhiên, REST path thường bị normalize bởi web server, reverse proxy, framework, hoặc HTTP client nội bộ. Vì vậy cùng một payload có thể hoạt động ở môi trường này nhưng không hoạt động ở môi trường khác.

Khi test REST path pollution, cần chú ý:

- Server decode URL bao nhiêu lần.
- Slash `/` có bị chặn hoặc encode lại không.
- Path traversal có bị normalize trước khi gửi tới backend không.
- Backend trả lỗi khác nhau giữa path không tồn tại và field bị cấm không.
- Có thể dùng ký tự hoặc encoding khác để bypass filter không.

### 6.3 Testing for server-side parameter pollution in structured data formats

Server-side parameter pollution không chỉ xuất hiện trong query string hoặc REST path. Nếu server dựng request nội bộ bằng structured data như JSON, XML, hoặc form object, attacker cũng có thể thử phá vỡ cấu trúc dữ liệu.

Ví dụ một request bên ngoài có thể chứa:

```json
{
  "username": "administrator"
}
```

Server sau đó dựng request JSON nội bộ:

```json
{
  "username": "administrator",
  "field": "email"
}
```

Nếu input không được xử lý đúng, attacker có thể thử chèn cấu trúc để thêm field mới, đổi kiểu dữ liệu, hoặc tạo duplicate key. Với JSON, cần lưu ý một số parser xử lý duplicate key khác nhau: parser này lấy key đầu tiên, parser khác lấy key cuối cùng. Với XML, có thể phát sinh thêm rủi ro liên quan đến entity, namespace, hoặc XPath nếu ứng dụng dùng dữ liệu đó để query.

Các hướng test phổ biến:

- Thêm field ngoài schema để xem server ignore hay xử lý.
- Gửi duplicate key trong JSON, ví dụ hai field `role` hoặc `field`.
- Đổi kiểu dữ liệu từ string sang array/object.
- Thử nested object nếu server dùng merge object không an toàn.
- Với XML, kiểm tra xem tag lạ hoặc entity có ảnh hưởng đến request nội bộ không.

Phản hồi lỗi từ parser rất hữu ích. Nếu lỗi báo rõ field, kiểu dữ liệu, hoặc object path, mình có thể suy luận cấu trúc request nội bộ và tiếp tục điều chỉnh payload.

### 6.4 Testing with automated tools

Automated tools giúp tăng tốc quá trình fuzz API, đặc biệt khi số lượng endpoint và parameter lớn. Trong Burp Suite, có thể dùng:

- Param Miner để tìm hidden header, query parameter, hoặc body parameter.
- Intruder để brute-force tên field, method, path, hoặc giá trị parameter.
- Repeater để kiểm chứng thủ công từng payload quan trọng.
- Scanner nếu có bản Pro để phát hiện một số lỗi API phổ biến.
- Logger/HTTP history để so sánh response theo status, length, timing.

Tuy nhiên, automated tools chỉ nên là lớp hỗ trợ. Với API vulnerabilities, lỗi thường nằm ở business logic và authorization context, nên tool khó hiểu được mục tiêu nghiệp vụ. Ví dụ tool có thể tìm ra endpoint nhận `PATCH`, nhưng việc `PATCH /api/products/1/price` cho phép user thường sửa giá sản phẩm hay không thì vẫn cần con người đánh giá.

Một workflow thực tế là:

- Dùng recon để tạo danh sách endpoint.
- Import documentation nếu có.
- Fuzz nhẹ parameter/method để tìm bề mặt ẩn.
- Kiểm chứng thủ công các endpoint có tác động nhạy cảm.
- Test lại bằng nhiều role: unauthenticated, user thường, owner, non-owner, admin nếu có.

### 6.5 Preventing server-side parameter pollution

Để phòng tránh server-side parameter pollution, nguyên tắc quan trọng nhất là không dựng request nội bộ bằng cách nối chuỗi trực tiếp từ input người dùng. Thay vào đó, nên dùng API client, URL builder, hoặc serializer an toàn để encode đúng từng thành phần.

Các biện pháp cụ thể:

- Validate input theo allowlist. Ví dụ username chỉ được chứa ký tự hợp lệ, không chứa `/`, `?`, `#`, `&`.
- Encode riêng từng context: path segment, query parameter, JSON value, XML value.
- Không cho user điều khiển tên parameter hoặc field nội bộ nếu không cần thiết.
- Khi backend nhận duplicate parameter, cấu hình hành vi rõ ràng và reject request mơ hồ.
- Không để endpoint nội bộ trả field nhạy cảm chỉ dựa trên parameter do client gián tiếp điều khiển.
- Tách rõ API public và API internal, không expose internal documentation ra ngoài.
- Log và cảnh báo các payload có ký tự bất thường như encoded slash, double encoding, path traversal, hoặc duplicate parameter.

Với REST path, nên dùng hàm encode path segment thay vì encode toàn bộ URL. Với query string, nên dùng object/map để builder tự encode key và value. Với JSON/XML, nên serialize dữ liệu từ object đã validate thay vì tự ghép text.

Cuối cùng, server nội bộ cũng cần tự enforce authorization và validation. Không nên giả định rằng request đi từ frontend server sang backend là an toàn, vì chính frontend server có thể bị attacker thao túng input để tạo request nội bộ độc hại.
